# DXソリューション提案エージェント

現場の業務課題・制約・業務量を自然文で伝えると、PoC として着手可能な DX 施策を提案するチャット型サービスです。  
生成 AI に丸投げするのではなく、課題抽出 → 制約チェック → 効果・コスト・ROI 試算までを Graph 上の専用ノードに分解し、制約を破る案は縮小して作り直します。

エンジニアの転職・採用担当者向けに、本リポジトリをポートフォリオとして紹介する文書です。

## サービスの背景・目的

> 以下はフォーマット用の下書きです。実際の動機・対象読者に合わせて書き換えてください。

### 背景（例）

- DX の相談では「生成 AI を使いたい」が先に立ちやすく、予算・期間・既存システム・セキュリティを無視した過大な提案になりがち
- 一方で、現場が渡せる情報は日報・転記・問い合わせ対応などの自然文が多く、要件定義書としては不足しやすい
- 情報が欠けているときに、確認せず ROI を断定したり、提案を出さずに止まったりすると、実務では使いにくい

### 目的（例）

- 現場担当者が、課題・制約・業務量をチャットで伝えるだけで、PoC 規模の DX 提案を得られるようにする
- 情報が足りない場合は仮説と確認質問を明示し、業務量が無い場合は ROI を断定しない
- 「LLM を呼ぶデモ」ではなく、制約遵守・実行可能性・費用対効果まで評価できるエージェントとして実装する

### 想定ユーザー（例）

- 社内の DX / 情シス / 業務改善担当
- 現場の課題をヒアリングし、最初の打ち手を整理したいコンサルタント

## 大まかな機能概要・特徴

ユーザーが業務状況を入力すると、エージェントが次をまとめて返します。

- **理解した課題**: 明示された課題を抽出。無い場合は状況から仮説課題を立て、仮説である旨を明示する
- **提案**: ルールベース / RPA / SaaS / 閉域 NLP / RAG など、カタログ上の解決パターンから PoC 案を 1 つ作る
- **対象範囲と導入手順**: 誰が何から着手するか、期間・役割まで具体化する
- **制約との対応**: 予算・期間・オンプレ / 機密 / 既存システム維持などを守れているかを検証する
- **KPI・効果・コスト・ROI**: 業務量があれば工数削減と投資回収を試算。無ければ断定せず確認する
- **リスクと対策**: 個人情報、運用負荷、誤判断などに対する緩和策を付ける
- **確認事項・置いた仮定**: 欠けている入力を隠さず、次に聞くべきことを返す

実装上の特徴は次のとおりです。

- **単一 LLM 呼び出しではない**: LangGraph で抽出・仮説・立案・検証・試算・要約をノード分割している
- **制約違反は作り直す**: 定性制約または予算超過があれば、最大 2 回まで縮小・再計画する
- **計算は決定論的**: 工数・費用合計・ROI は LLM に任せず、ツール側で算出する
- **過大な生成 AI を避ける**: 単純な転記や少額・短期間の案件では、iPaaS / RPA / マクロを優先する
- **会話 UI**: Streamlit 上でパスワード認証、チャット履歴の保存・切り替え・削除ができる

## 使い方

1. 上記 URL を開き、パスワードを入力する
2. チャット欄に、次の情報をできるだけ具体的に書く（欠けていても動く）
   - 部門・現状の業務
   - 解決したい課題
   - 対象人数・頻度・1 件あたり時間
   - 予算・期間・セキュリティ / 既存システムの制約
3. エージェントが提案（または確認質問）を返す
4. 必要なら追加情報を送り、会話を続ける
5. 左サイドバーから新しいチャットの開始、過去会話の再開・削除ができる

入力例:

```text
営業では、全国の営業担当者300名が訪問記録を日報システムへ自由記述しています。
管理職が全文を読んで案件を把握しており、フォーマットがバラバラで定量化できません。
業務量は 300名、1人1日1件、20分です。
初期予算500万円以下、既存のオンプレ日報システムと連携、半年以内に本稼働したいです。
DXの提案をお願いします。
```

ローカル起動（開発者向け）:

```bash
uv sync
cp .env.example .env  # OPENAI_API_KEY / OPENAI_MODEL / APP_PASSWORD を設定
uv run streamlit run src/dx_sol_suggest/main.py
```

Docker でも起動できます。

```bash
docker compose up --build
```

## オリジナリティー・工夫点

### Graph 構造

チャットボットを 1 本のプロンプトにせず、状態付きワークフローとして設計しています。

```text
START
  → 課題抽出
      ├─ 課題あり → 制約抽出
      └─ 課題なし → 仮説立案
                      ├─ 仮説可 → 制約抽出
                      └─ 材料不足 → 要約（確認質問のみ）
  → 解決策立案
  → 制約チェック ── 違反なら立案へ戻る（最大 2 回）
  → 効果試算 ∥ コスト試算（並列）
  → 予算チェック ── 超過なら縮小フラグ付きで立案へ戻る
  → ROI 試算
  → 要約
END
```

工夫した点:

- **抽出と仮説を分ける**: ユーザーが言っていない課題を、抽出段階で捏造しない
- **ルール制約と定性制約を分ける**: パブリック LLM 禁止・全面リプレイス禁止などはコードで判定し、公平性・正確性などは LLM で判定する
- **再計画ループ**: 違反理由と修正ヒントを state に残し、次の立案へフィードバックする
- **予算超過時はスケールダウン**: ML / カスタム開発を候補から外し、安価なパターンへ切り替える
- **効果とコストは並列実行**: 互いに依存しない試算を同時に走らせ、合流後に予算判定する
- **構造化出力**: 各ノードは Pydantic スキーマで LLM 出力を拘束し、後段ツールが数値計算できる形にする

「LLM に提案させる」部分は立案・定性チェック・要約に限定し、カタログ参照・制約判定・費用対効果はプログラム側の責務にしています。

### LLM-as-a-Judge

提案品質を人手の印象だけでなく、評価用データセットと LLM 審査で測れるようにしています。

- **評価基盤**: RAGAS（`RubricsScore` + `AspectCritic`）+ GPT-4o を審査モデルに使用
- **共通 6 観点（1〜5 点）**
  - 課題整合性
  - 制約遵守
  - 実行可能性
  - ビジネス価値
  - リスク認識
  - 回答構造
- **ケース固有判定（Yes / No）**: 情報量に応じた振る舞いが正しいか
  - 十分なら提案する（`suggest`）
  - 不足なら提案せず聞く（`ask`）
  - 仮定を明示して提案する（`ask_or_assume`）
  - 業務量なしで ROI を断定しない（`refuse_overconfident_roi`）

データ側の工夫:

- 営業・採用・シフト・経費など、現場寄りのベースケースを用意
- 同じケースから課題 / 制約 / 業務量を欠落させた派生ケースを生成
- 構造化入力と自然文入力の両方を評価
- 含めるべき要素と、やってはいけない要素（全面リプレイス、パブリック LLM など）をケースごとに定義

これにより、「それっぽい提案」ではなく、制約を守り、情報不足時の振る舞いまで含めて改善できる状態にしています。

## 大変だった点・その対策

### データセットの用意

**困った点**  
「良い DX 提案」は正解が一つではなく、予算・期間・セキュリティで大きく変わる。単純な Q&A データでは、過大な生成 AI 提案や、情報不足時の ROI 断定を検出できない。

**対策**

- 部門別のベースケースを先に作り、そこから項目欠落・入力形式（構造化 / 自然文）の派生ケースを生成した
- 各ケースに `expected_behavior` と、含めるべき要素 / 禁止要素を持たせた
- 共通ルーブリックとケース固有の AspectCritic を分け、汎用品質と個別の振る舞いを同時に見るようにした

### Graph 設計

**困った点**  
抽出・仮説・立案・検証・試算を 1 ノードにまとめると、失敗原因が分からず、制約違反時に同じ案を繰り返しやすい。一方でノードを増やしすぎると、状態の受け渡しとループ条件が複雑になる。

**対策**

- 「ユーザーが明示した事実」と「システムが置いた仮説」を state 上で分離した
- 定量制約はコード、定性制約は LLM、という役割分担にした
- 再計画は無限ループにせず `max_retries=2` で打ち切り、打ち切り時は仮定・確認事項として残す
- 効果試算とコスト試算は並列化し、予算判定だけ合流後に行うようにした

### デプロイ

**困った点**  
Streamlit はローカル既定ポートと Cloud Run の `PORT` が異なり、秘密情報の扱いもローカルの `.env` と本番で分けないと事故が起きやすい。GitHub から GCP へデプロイする認証も、キーをリポジトリに置きたくない。

**対策**

- Docker イメージは `PORT` 環境変数を見て起動するようにした
- OpenAI API キーとアプリパスワードは Secret Manager 経由で Cloud Run に注入した
- GitHub Actions は Workload Identity Federation で認証し、サービスアカウントキーを置かないようにした
- `main` への push で Artifact Registry へイメージ push → Cloud Run へデプロイするパイプラインにした

## 今後の展望

> 優先度の高い順に、これからやりたいことを記載しています。必要に応じて取捨選択してください。

1. **評価の定常化**: 全テストケースでの回帰評価、プロンプト変更前後のスコア比較を CI に載せる
2. **カタログの拡充**: 業種・部門ごとの典型課題と、より現実的な費用レンジを増やす
3. **会話の永続化**: 現状はセッション内の履歴のみ。ユーザー単位で提案履歴を保存し、再訪できるようにする
4. **提案の比較**: 1 案固定ではなく、制約内の代替案（安価案 / 本命案）を並べて提示する
5. **人間のフィードバック**: 採用担当・現場担当が「採用 / 却下」した理由を学習データへ戻す
6. **認証の強化**: デモ用パスワードから、組織向けの適切な認証へ置き換える
7. **マルチターンの要件定義**: 不足項目を対話で埋め、仮説を確定してから最終提案するモードを分ける
